# GenAI exercise

This document covers two things. First, the GenAI exercise from the brief: the prompt I'd use to generate a Task Management REST API, the code it produced, and how that output was validated and corrected. Second, an honest account of how this Pokédex API was built with AI, including where the AI was wrong.

## 1. The prompt

This is the exact prompt, written to be reused as is. Every requirement in it can be checked, so the output can be validated against it item by item (section 3).

````text
You are a senior Java backend engineer. Generate a complete, production-quality Task Management
REST API as a standalone Maven project. Write real, compiling code: no placeholders, no TODOs.

## Stack (use exactly these)
- Java 21, Spring Boot 4.1.1 (spring-boot-starter-parent), Maven.
- Spring Web MVC, Bean Validation, Spring Data JPA, Spring Security OAuth2 Resource Server (JWT).
- PostgreSQL 16 with Flyway migrations; Hibernate `ddl-auto=validate` (Flyway owns the schema).
- Tests: JUnit Jupiter, Spring Boot Test, spring-security-test, Testcontainers PostgreSQL.
  Do not use H2 or any in-memory database.
- Base package: com.example.tasks. Constructor injection only. Java records for DTOs. No Lombok.

## Domain
- User: id (UUID), username (unique, 3-30 chars). Users are created elsewhere, but create the
  `users` table in the migrations.
- Task: id (UUID, generated by the server), owner (the User it belongs to, required),
  title (required, 1-120 characters after trimming), description (optional, at most 2000
  characters), status (TODO | IN_PROGRESS | DONE, default TODO), dueDate (optional ISO-8601
  date, no time part), createdAt, updatedAt, version (optimistic locking).

## Authentication and authorization
- Stateless JWT bearer tokens signed with HS256; the secret comes from the environment variable
  TASKS_JWT_SECRET (at least 32 bytes, fail at startup otherwise).
- The token's `sub` claim is the username. Resolve it to the `users` row on every request; if no
  such user exists, answer 401.
- Every endpoint requires authentication.
- A user can only read and change their own tasks. Another user's task must answer 404 (never
  403), so task ids don't reveal that the task exists.

## Endpoints (all under /api/v1/tasks, JSON)
- POST   /            create; 201 with a Location header and the task.
- GET    /            the caller's tasks, paginated: page (>= 0, default 0), size (1-100,
                      default 20); optional filters status and dueBefore (date). Order by dueDate
                      ascending with tasks without a due date last, then createdAt. Response:
                      { content, page, size, totalElements, totalPages }.
- GET    /{id}        one task; 404 if missing or not the caller's.
- PUT    /{id}        replace title, description, status and dueDate. The body must include the
                      `version` the client read; a different version answers 409.
- PATCH  /{id}/status { "status": ... } changes only the status.
- DELETE /{id}        204.
- A task response contains id, title, description, status, dueDate, createdAt, updatedAt and
  version. Never return JPA entities from controllers.

## Validation and errors
- Every error is an RFC 7807 problem detail (application/problem+json) with type, title, status,
  detail, instance, and an `errors` array of { field, message } for field-level problems.
- 400 for: blank or too long title, too long description, an unknown status value, a malformed
  date, malformed JSON, unknown JSON members, page/size out of range, and a malformed UUID in the
  path. Name the offending field in `errors`.
- dueDate must not be in the past when a task is created, or when an update changes it. An
  existing overdue task can still be edited if its due date is left unchanged. "Today" is the
  current date in UTC; inject a java.time.Clock so this is testable.
- 401 without a token or with an invalid token, 404 as above, 409 for a stale version.
- Never put stack traces or exception class names in responses.

## Code structure
- Packages: task (domain service and rules), persistence (JPA entities, Spring Data
  repositories), web (controller, request/response records, mapper, exception handler), security
  (security configuration).
- Service methods are transactional. Keep controllers thin.

## Tests (they must pass)
- Web slice tests (@WebMvcTest with jwt() from spring-security-test) covering every status code
  listed above.
- Unit tests for the service: the due-date rule (create, update with the same date, update with
  a new past date) and ownership (another user's task is not found).
- One Testcontainers integration test: create a task, list returns only the caller's tasks,
  update with a stale version returns 409, delete returns 204 and the task is gone.

## Output format
Print every file of the project with its relative path as a heading, in this order: pom.xml,
src/main/resources/application.yml, the Flyway migration(s), main code, tests. After the code,
list every assumption you made.
````
